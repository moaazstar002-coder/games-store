# فرز المشاكل قبل النشر القادم

تاريخ المراجعة: 2026-11-25

> تمت مراجعة الكود وإعدادات النشر والاختبارات المحلية، وفُحص الدومين المنشور في المتصفح. لم نتمكن من قراءة إعدادات Environment Variables داخل Vercel أو Render.

## الخلاصة

**الموقع المنشور لا يصل حاليًا إلى الـAPI:** الواجهة تطلب الألعاب والتصنيفات من `localhost:8000`، والطلب يفشل للزائر. أصلحوا ذلك أولًا. المشروع شخصي والدفع ديمو، لذلك لا نعتبر عدم وجود تحصيل حقيقي مانعًا للنشر؛ فقط يجب ألا يُفهم الديمو على أنه دفع فعلي.

## نتيجة فحص الدومين المنشور

على `https://games-store-plum.vercel.app/` ظهرت الواجهة، لكن طلبات الألعاب والتصنيفات ذهبت إلى `http://localhost:8000/api/v1/...` وفشلت برسائل CORS و`ERR_FAILED`. عنوان `localhost` هنا يعني جهاز كل زائر، وليس الـBackend المنشور؛ لذلك الكتالوج والأنواع لا يمكن تحميلهما للمستخدمين.

**الإصلاح الأول:** انشر Backend قابلًا للوصول، واضبط `VITE_API_BASE_URL` في Vercel على عنوانه مع `/api/v1`، ثم أعد بناء ونشر الواجهة. بعد النشر اختبر طلب الألعاب والأنواع من نفس الدومين.

## مانع تشغيل الموقع المنشور

### P0 — الواجهة المنشورة تستدعي API على localhost

على `https://games-store-plum.vercel.app/` ظهرت الواجهة، لكن طلبات الألعاب والتصنيفات ذهبت إلى `http://localhost:8000/api/v1/...` وفشلت برسائل CORS و`ERR_FAILED`. عنوان `localhost` هنا يعني جهاز كل زائر، وليس الـBackend المنشور؛ لذلك الكتالوج والأنواع لا يمكن تحميلهما للمستخدمين.

**الإصلاح:** استضف FastAPI على Vercel أو عنوان API عام آخر، واضبط `VITE_API_BASE_URL` على عنوانه مع `/api/v1`، ثم أعد نشر الواجهة. الكود المحلي الآن لا يستخدم localhost في الإنتاج إذا غاب المتغير، ويعرض فشل تحميل بدل إرسال الطلب لجهاز الزائر. الموقع المنشور لن يستفيد من التعديل إلا بعد نشر نسخة جديدة.

**الأدلة:** `src/lib/api.js`، `src/lib/apiConfig.js`، `BackEnd/app/main.py`.

### P1 — إعدادات Backend وFrontend على Vercel

- أنشئ مشروع Vercel للـBackend وحدد `BackEnd` كـRoot Directory؛ ملف `BackEnd/main.py` يصدّر تطبيق FastAPI كمدخل واضح لـVercel، وإصدار Python 3.13 محدد في `BackEnd/.python-version`. إعداد `vercel.json` في الجذر خاص بإعادة كتابة مسارات SPA في مشروع الواجهة ولا يخلط المشروعين.
- في مشروع Backend اضبط `DATABASE_URL` pooled من Neon، لكن غيّر بادئته إلى `postgresql+psycopg://` لأن `requirements.txt` يثبت psycopg 3. أضف `SECRET_KEY` جديدًا و`FRONTEND_ORIGINS=https://games-store-plum.vercel.app`.
- في مشروع الواجهة اضبط `VITE_API_BASE_URL` إلى `https://<backend-project>.vercel.app/api/v1` ثم أعد النشر؛ القيمة تُضمّن وقت بناء الواجهة.
- `DATABASE_URL_UNPOOLED` و`NEON_BRANCH` الموجودان في `.env` لا يقرأهما التطبيق، فلا تضفهما إلى Vercel.

**المطلوب منك:** إنشاء المشروعين وضبط المتغيرات في لوحة Vercel؛ لا نملك صلاحية لهذه الإعدادات من المستودع.

**الأدلة:** `render.yaml`، `BackEnd/app/core/config.py`، `README.md`.

## بديل Render مجاني ولا يتطلب بطاقة جديدة

**الأنسب لحالتكم: استضافة FastAPI على Vercel نفسه** بدل إضافة مزود آخر؛ الموقع موجود أصلًا على Vercel. توثيق Vercel يشرح تشغيل FastAPI على Python Runtime كـVercel Function. خطة Hobby مجانية، وحدودها المنشورة تشمل مليون استدعاء Functions شهريًا و4 ساعات CPU نشطة؛ إذا تجاوزتوا الحد قد تتوقف الميزة حتى دورة الاستخدام التالية. صفحة الخطة تطلب بطاقة عند الترقية إلى Pro، وليس لاستخدام ميزات Hobby المذكورة.

لربط هذا المشروع، أنشئ مشروع Vercel ثانيًا من نفس المستودع وحدد `BackEnd` كـRoot Directory. أضف متغيرات البيئة المذكورة أعلاه، ثم ضع عنوان المشروع في `VITE_API_BASE_URL` لمشروع الواجهة وأعد نشرها. التطبيق الحالي ينفذ التهيئة والترحيل والبذر عند بدء الـBackend؛ راقبوا سجلات أول تشغيل وتأكدوا من قاعدة Neon قبل استخدامه.

مصادر رسمية: [FastAPI على Vercel](https://vercel.com/docs/frameworks/backend/fastapi)، [خطة Hobby وحدودها](https://vercel.com/docs/plans/hobby)، [Python Runtime](https://vercel.com/docs/functions/runtimes/python).

**ليس خيارًا مناسبًا مجانيًا بديلًا:** Hugging Face Spaces؛ توثيقهم يقول إن Docker Spaces (الأنسب لتشغيل FastAPI) تحتاج خطة مدفوعة، رغم وجود Spaces ثابتة مجانية.

### P1 — مجموعة اختبارات الواجهة حمراء في CI

فشل 8 من 62 اختبارًا محليًا: اختبارات السلة والمفضلة تتوقع reducers بلا `toast`، بينما الـreducers تستدعي الإشعارات. وملف GitHub Actions يشغّل `npx vitest run` على كل push وPR إلى `main`، لذلك سيظل فحص CI فاشلًا حتى تُحل المشكلة أو يُراجع التوقع المقصود.

**قبل النشر عبر CI:** انقل الإشعارات خارج reducers مع الحفاظ على سلوك الواجهة، ثم شغّل مجموعة الاختبارات كاملة. لا تتجاوز الاختبارات الحمراء لمجرد تمرير النشر.

**الأدلة:** `src/store/slices/CartSlice.js`، `src/store/slices/WishlistSlice.js`، `src/test/CartSlice.test.js`، `src/test/WishlistSlice.test.js`، `.github/workflows/test.yml`.

### P1 — تأكيد قاعدة البيانات وخطة التهيئة والترحيل

بدء الـBackend ينفّذ `create_all` والترحيل وتهيئة الكتالوج تلقائيًا. الترحيل الحالي يضيف عمود `role` عند غيابه، والتهيئة قد تضيف بيانات الألعاب/التصنيفات إذا لم تكن موجودة. تحديث صفحات Consoles وAccessories يضيف جدولي `consoles` و`accessories`، ويجعل `order_items.game_id` اختياريًا ويضيف مراجع للمنتجين الجديدين. البذر يضيف 4 أجهزة و6 إكسسوارات تجريبية بصورة idempotent. المنتجات القديمة في الصفحتين كانت بيانات ثابتة داخل الواجهة، وليست سجلات في قاعدة البيانات؛ لذلك لا توجد سجلات قديمة من الصفحتين لحذفها.

لا توجد في إعداد النشر خطوة ترحيل مستقلة أو خطة تراجع موثقة.

بدأ الـBackend محليًا مرة واحدة باستخدام PostgreSQL الموجود في `.env`؛ سجل التهيئة قال إنه أضاف صفر ألعاب وتصنيفات، لكن الترحيل نُفّذ. أوقفنا هذا الاتصال، والـBackend الجاري يستخدم SQLite معزولة.

**المطلوب منك قبل النشر:**
1. تأكد أن `DATABASE_URL` في مشروع Backend على Vercel يشير إلى قاعدة Neon المقصودة، وخذ نسخة احتياطية قبل الترحيل.
2. انشر Backend أولًا، وراجع سجلات بدء التشغيل للتأكد من نجاح تعديل `order_items` وإنشاء الجدولين وإضافة المنتجات التجريبية.
3. اختبر `GET /api/v1/consoles` و`GET /api/v1/accessories` و`/docs` على رابط Backend، وتأكد أن الطلبات من أصل الواجهة مسموح بها عبر CORS.
4. بعد نجاح Backend، انشر الواجهة وتأكد من أن `VITE_API_BASE_URL` يشير إلى `/api/v1` في Backend الصحيح.

لا تحذف بيانات قاعدة الإنتاج يدويًا؛ المنتجات القديمة في الصفحتين كانت بيانات ثابتة في الواجهة وليست سجلات. لا تستخدم قاعدة إنتاج من تشغيل التطوير المحلي.

**الأدلة:** `BackEnd/app/main.py`، `BackEnd/scripts/migrate.py`، `BackEnd/scripts/seed.py`، `render.yaml`.

## ملاحظات لا تمنع نشر المشروع كديمو

### P2 — الدفع والإجمالي سلوك ديمو

صفحة checkout تعرض وسائل دفع وضريبة 5% وكوبونًا، لكن الـBackend ينشئ طلبًا بحالة `pending` دون مزود دفع، ولا يطبق الضريبة أو الكوبون على الإجمالي. هذا لا يمنع نشر مشروع شخصي إذا ظل الدفع تجريبيًا بوضوح؛ لا تستخدموه لتحصيل أموال حقيقية.

**الأدلة:** `src/pages/Checkout.jsx`، `BackEnd/app/modules/orders/service.py`، `BackEnd/app/modules/orders/models.py`.

### P2 — اختبارات الـBackend غير موجودة في CI

اختبارات Backend الـ11 نجحت محليًا باستخدام `python -m unittest discover -s tests -v`، لكنها غير مشمولة في `.github/workflows/test.yml`. أضف خطوة تشغيلها لتحسين التحقق الآلي.

### مراجعة مطلوبة قبل النشر — تحذيرات اعتماديات npm

أظهر `npm install` بعد إضافة مزود تغطية Vitest عدد 15 تحذيرًا أمنيًا (4 متوسطة و11 عالية). لم تُراجع تفاصيل الحزم المتأثرة أو ما إذا كانت ضمن اعتماديات الإنتاج.

**المطلوب منك:** شغّل `npm audit` وراجع اعتماديات الإنتاج والتحذيرات العالية قبل النشر؛ لا تطبق `npm audit fix` تلقائيًا دون مراجعة التغييرات.

### P2 — صورة واحدة لا تُحمّل

فحص الصفحة الرئيسية وجد صورة واحدة مكسورة من أصل 17؛ طلب Unsplash فشل في بيئة الفحص بـ`ERR_BLOCKED_BY_ORB`. تحقق من الدومين المنشور/شبكة المستخدمين، واستبدلها بصورة محلية أو مصدر موثوق إذا كانت المشكلة متكررة. ليست مانعًا إلا إذا كانت الصورة جزءًا أساسيًا من واجهة البيع.

### P3 — تحذيرات CSS غير مانعة

`npm run build` ينجح، مع تحذيرين عن الخاصية `file` في CSS مولّد (`[file:line]` و`[file:lines]`). هذه النصوص موجودة في ملفات `.agents`؛ راجع مصادر Tailwind لاحقًا إذا أردت تنظيف التحذيرات.

## نتائج التحقق المحلي

| الفحص | النتيجة |
|---|---|
| `npm run build` | نجح، مع تحذيري CSS |
| `npm run lint` | نجح |
| اختبار إعداد API المستهدف | 3 ناجحة |
| `npm run test -- --run` | 54 ناجح، 8 فاشل (62 إجمالًا؛ الفشل القديم في السلة والمفضلة) |
| اختبارات الكتالوج والسلة والـcheckout المركزة | 13 ناجحة |
| تغطية `useCatalogProducts` و`CatalogProductsPage` | 90.24% إجماليًا؛ 87.5% فروع |
| `python -m unittest discover -s tests -v` من `BackEnd` | 11 ناجحة |
| `/docs` و`/api/v1/consoles` و`/api/v1/accessories` وCORS محليًا | HTTP 200 |
| معاينة production build بدون `VITE_API_BASE_URL` | لا يرسل طلبًا إلى localhost؛ يعرض خطأ تحميل الألعاب مع زر إعادة المحاولة |

`pytest` غير مثبت، لكن الاختبارات الحالية مكتوبة بـ`unittest` ولا تحتاجه.

## ترتيب التنفيذ المقترح

1. **انشر FastAPI على Vercel** باستخدام `BackEnd` كجذر المشروع، واضبط `DATABASE_URL` و`SECRET_KEY` و`FRONTEND_ORIGINS`.
2. **اضبط `VITE_API_BASE_URL`** في مشروع الواجهة على عنوان Backend وأعد النشر؛ تحقق أن طلبات الألعاب والتصنيفات لا تذهب إلى `localhost`.
3. **أصلح اختبارات reducers** حتى ينجح فحص CI.
4. وضّح أن الدفع ديمو، ثم أضف اختبارات Backend إلى CI. الصورة والتحذيرات تحسينات لاحقة.
